## 4. Critical Conventions (REUSE — Don't Redesign)

### LoggerMessage Source-Gen Patterns (Stable after 16 phases)

Three reuse patterns. All proven across services, controllers, page models, and Program.cs:

#### Pattern A: One method per call site
Every log call gets a unique partial method. Right when templates are all distinct. Used in NotificationService, GriffinConfigService, GriffinService, DatabaseBackupService.

#### Pattern B: Method reuse via `Endpoint` parameter
V1 controllers share boilerplate (endpoint disabled, unauthorized, DB error, unexpected error) across 5+ endpoints distinguished only by the endpoint name. ONE shared method per template, called with `nameof(EndpointMethodName)` as the `Endpoint` argument. Used in SwapRequests, TimeOff, Chores, OnDuty, Users V1, Feedback.

#### Pattern C: Template parameterization
Repeated templates differing only by a verb / entity get the verb extracted as `{Action}` (or `{Entity}` etc.). Used in Calendar/Table, Requests/Index, Pages/Admin/Users (mixed with Pattern A), Program.cs (one method, 5 sites).

#### Pattern C variant: bare-vs-suffixed templates (Phase 8)
When a literal recurs verbatim with optional suffixes, use one method for the bare form + distinct methods for each suffix variant. **Do not** parameterize the suffix as `{Context}` — produces ugly call-site strings with embedded leading spaces.

### Type Signature Lessons Learned

`[LoggerMessage]` requires concrete signatures. Recurring pitfalls:

| Source-site value | Correct partial signature | Notes |
|---|---|---|
| `int?` | `int? userId` | Match nullability exactly |
| `string?` (raw claim) | `string? companyId` | V1 controllers commonly have BOTH `int companyId` (parsed success-path) AND `string? companyId` (raw catch-block claim). Keep distinct. |
| `int` (parsed) | `int companyId` | |
| `PathString` | `PathString path` | Requires `using Microsoft.AspNetCore.Http;` |
| Enum types in `ShiftManager.Models.Support` | Same enum type | **Phase 14 pitfall**: `using ShiftManager.Models;` is NOT enough for `UserRole` / `MoleculeType` / `OnDutyType` — explicit `using ShiftManager.Models.Support;` required |
| `Exception` | `(ILogger logger, System.Exception ex, ...)` | **Position matters** — must immediately follow `ILogger logger`. Source-gen detects positionally. |

**Format specifiers** like `{SizeKB:F1}`, `{Mode}` are valid in source-gen `Message` templates — preserve verbatim from original.

**Two distinct CompanyId types in V1 controllers**: keep them as separate partial methods — don't try to coerce.

**For Program.cs specifically**: three local logger variables exist (`logger`, `startupLogger`, `featureFlagLogger`), all `ILogger<Program>`. The same partial methods serve all three; call sites pass whichever local is in scope.

## 6. Anti-Patterns to Avoid

1. **Don't trust dedup-chain-canonical findings without verification.** ~30% of HiddenBugs lens findings were factually invalid in prior sprints.
2. **Don't add defensive code "just in case."** Invalid findings get verification logged, NOT a null check that compensates for a non-bug. CLAUDE.md §4.
3. **Don't bulk-migrate API call sites without per-site review.** F-C-006 warned about response-shape drift.
4. **Don't fix CA1860 (`.Any()` → `.Count > 0`) with global sed.** Catches `IQueryable<T>` and breaks SQL translation.
5. **Don't squash migrations without deployment-coordination plan.** Air-gapped deployments at unknown migration points.
6. **Don't try multiple LoggerMessage files in one PR — UNLESS user explicitly authorizes parallel dispatch.** Phases 9-15 demonstrated parallel dispatch works when (a) each file has independent EventId range, (b) each agent has explicit no-build / no-shared-doc / no-commit constraints, (c) integration build + tests are run by orchestrator after all agents complete. Phase 16 was solo because Program.cs is special (top-level statements, multiple local logger variables).
7. **Don't add `TreatWarningsAsErrors` until Batches K and L Slice 10+ close.** With ~1,888 warnings still expected after Phase 16 verification, flipping it turns every PR into a build failure. Only enable after warnings are below ~50.
8. **Don't run `dotnet build --no-incremental` during a focused edit cycle** unless you need the warning baseline. It can rewrite `packages.lock.json` as a side-effect.
9. **Don't `taskkill` ShiftManager.exe.** Permission hook blocks it. User terminates manually.
10. **Don't break existing test mocks when changing constructor signatures.** When migrating PageModels to inject new services (like `IBackgroundTaskQueue` instead of `IServiceScopeFactory`), grep `ShiftManager.Tests/` for `new SignupModel(...)`-style constructor calls and update mocks.
11. **Don't try to coerce `int` and `string?` companyId types into one partial method.** V1 controllers genuinely have both — keep distinct signatures.
12. **Don't reuse a partial method's name across classes.** Each LoggerMessage method is class-scoped. EventIds are global.
13. **Don't filter CA1848 counts with bare filename substring**. `"Users.cshtml.cs"` matches `LockedUsers.cshtml.cs` and `GetEligibleUsers.cshtml.cs` too — use `"Admin\\Users.cshtml.cs"` (escaped backslash for PowerShell regex).
14. **Don't parameterize a suffix when it would embed leading whitespace at call sites.** Distinct methods are cleaner than `{Context}` placeholder for "Invalid claim during X" variants.
15. **Don't import the wrong `ShiftManager` namespace for enums.** `UserRole`, `MoleculeType`, `OnDutyType`, `RequestStatus`, `NotificationType`, `TimeOffType` all live in `ShiftManager.Models.Support` — NOT `ShiftManager.Models`. This was the integration-fix in Phase 14.
16. **Don't remove `public partial class Program { }` from the bottom of `Program.cs`.** Load-bearing for `WebApplicationFactory<Program>` integration tests.
17. **Don't trust a build that fails at the link/copy step.** The C# compile + analyzer pass may have completed, but stale obj/ artifacts can mislead. Always re-run `--no-incremental` after the lock is released.
18. **Don't run parallel agents on overlapping files.** Per-file isolation is what makes parallel dispatch safe — agents editing the same source corrupt each other's work.
