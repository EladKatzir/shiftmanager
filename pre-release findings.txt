1. CRITICAL SECURITY ISSUES
────────────────────────────────────────────────────────────────────────────────

[Category] security
[File/Section] Services/TenantResolver.cs:55
[Description] CRITICAL DATA LEAK: Unauthenticated requests fall back to CompanyId=1.
This means any unauthenticated request can access Company 1's data through query
filters. While most pages require authentication, any page or API that doesn't
explicitly require auth will leak Company 1 data. The comment "TODO Phase 3:
Remove this fallback" acknowledges this but it should be removed immediately.
[Recommendation]
- Remove the fallback to CompanyId=1 completely
- Return 0 or throw an exception when tenant cannot be determined
- Add explicit handling for unauthenticated scenarios where needed
- Run security audit to identify any unauthenticated endpoints

[Category] security
[File/Section] Data/AppDbContext.cs:248-276
[Description] CRITICAL MULTI-TENANT DATA LEAK: Query filters are NOT applied to:
- AppUser (users table)
- AppConfig (configuration)
- RoleAssignmentAudit
- UserJoinRequest
- DirectorCompany

This means code that queries these entities directly will see data from ALL
companies without CompanyId filtering. For example, db.Users.ToList() would
return users from all companies. This is a catastrophic security vulnerability.
[Recommendation]
- Add query filters for ALL tenant-scoped entities
- Add this to AppDbContext.cs OnModelCreating:
  modelBuilder.Entity<AppUser>()
    .HasQueryFilter(e => e.CompanyId == _tenantResolver.GetCurrentTenantId());
  (repeat for AppConfig, RoleAssignmentAudit, UserJoinRequest)
- DirectorCompany should NOT have a filter (it's the mapping table)
- Add integration tests to verify query filters work
- Run security audit to check if any existing code leaked data

[Category] security
[File/Section] Data/CompanyIdInterceptor.cs:87-106
[Description] SECURITY BYPASS: Interceptor only sets CompanyId if it's 0. If a
developer explicitly sets entity.CompanyId to a different company's ID, the
interceptor won't validate or prevent it. This allows cross-tenant data insertion.
[Recommendation]
- Add validation: if (entry.Entity.CompanyId != 0 && entry.Entity.CompanyId != companyId)
  throw new InvalidOperationException($"Cannot save entity to different tenant...")
- Or: Always override CompanyId regardless of current value (more secure)
- Add option to disable override for system operations (seeding, migrations)

[Category] security
[File/Section] Program.cs:71
[Description] Cookie expiration is 7 days, which may be too long for sensitive
workforce management data. Consider reducing for better security posture.
[Recommendation]
- Reduce to 1-2 days for production environments
- Make configurable via appsettings.json
- Consider shorter expiration for high-privilege roles (Owner, Director)
- Add "Remember Me" checkbox for longer sessions if needed

2. PERFORMANCE ISSUES
────────────────────────────────────────────────────────────────────────────────

[Category] performance
[File/Section] Data/CompanyIdInterceptor.cs:58
[Description] PERFORMANCE BOTTLENECK: Creates new DI scope on EVERY SaveChanges
call via _serviceProvider.CreateScope(). This is expensive and unnecessary.
The interceptor is registered as Singleton but needs to access scoped services,
leading to this anti-pattern. On high-traffic sites, this will create thousands
of unnecessary scopes per minute.
[Recommendation]
- Refactor interceptor to be Scoped instead of Singleton
- Inject ITenantResolver directly in constructor
- Update Program.cs registration: builder.Services.AddScoped<CompanyIdInterceptor>()
- Update DbContext registration to get interceptor from scope

[Category] performance
[File/Section] Services/TenantResolver.cs:27,39,44,50
[Description] Excessive logging at Information level on every GetCurrentTenantId()
call. This method is called on EVERY database query due to query filters. With
hundreds of queries per request, this will spam logs and impact performance.
[Recommendation]
- Change logging level to Debug or Trace
- Or: Remove logging entirely and only log warnings/errors
- Add logging only in exceptional cases (missing claim, fallback used)
- Consider metrics instead of logs for monitoring tenant resolution

[Category] performance
[File/Section] Data/AppDbContext.cs:37-43
[Description] DateOnly.Parse() is used without error handling. If database
contains invalid date strings, parsing will throw exceptions at runtime,
potentially crashing the application. SQLite stores dates as strings, so
corruption is possible.
[Recommendation]
- Use DateOnly.TryParse() with validation
- Return a default value or null on parse failure
- Add data validation migration to clean corrupt dates
- Log warning when parse fails for monitoring

[Category] performance
[File/Section] Data/AppDbContext.cs (missing indexes)
[Description] Missing indexes on frequently queried columns:
- UserNotification.IsRead (queried for unread count)
- Users (CompanyId, Email) composite - faster tenant-scoped email lookups
- ShiftAssignment.UserId alone - for user's shift queries
- TimeOffRequest.Status - for filtering by status
- SwapRequest.RequesterId - for user's swap requests
These missing indexes will cause full table scans as data grows.
[Recommendation]
- Add composite index: .HasIndex(u => new { u.CompanyId, u.Email }) on Users
- Add index: .HasIndex(n => n.IsRead) on UserNotification
- Add index: .HasIndex(a => a.UserId) on ShiftAssignment
- Add index: .HasIndex(t => t.Status) on TimeOffRequest
- Add index: .HasIndex(s => s.RequesterId) on SwapRequest
- Run EXPLAIN QUERY PLAN on slow queries to verify improvements

[Category] performance
[File/Section] Program.cs:108
[Description] await db.Database.MigrateAsync() runs on every application startup.
For production deployments with multiple instances starting simultaneously, this
can cause migration conflicts and slow startup. Migrations should be applied
separately in production.
[Recommendation]
- Only run MigrateAsync() in Development environment
- In Production: require migrations be run manually or via deployment pipeline
- Add startup check: if (!app.Environment.IsDevelopment()) { await db.Database.EnsureCreatedAsync(); }
- Document migration procedure in deployment guide

[Category] logic
[File/Section] Data/AppDbContext.cs:217-220
[Description] Unique constraint on Chore includes CanceledAt in the index:
.HasIndex(c => new { c.CompanyId, c.UserId, c.Date, c.CanceledAt }).IsUnique()
This means you cannot have duplicate CANCELED chores on same day. The filter
